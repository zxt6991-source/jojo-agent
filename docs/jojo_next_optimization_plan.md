## 1. 目标与现状

下一阶段围绕三条主线推进：**执行可靠性、长会话性能、产物交付完整性**。先让任务完成状态可信、异常后能够继续使用，再降低长历史的运行成本，最后扩展高频产物预览与跨平台交付。

当前已经具备以下基础：

- Desktop 与 Headless Server 复用 Runtime / App Service 公共边界。
- 权限治理、审批、会话持久化、上下文压缩、工具循环保护已经存在。
- Spawn、Persistent Team、Workflow、Durable Scheduler 与 Channel 已经形成完整能力模块。
- Artifact Contract、`ToolResult.artifacts`、`show_artifact`、成功文件修改的交付识别、右侧预览、会话内容授权与 HTTP 内容 API 已经落地。
- CI 已包含 lint、类型检查、Vitest、Electron E2E 和 Desktop package。

本方案不重复立项上述已完成能力。Artifact 当前状态以 [原优化方案头部](jojo_artifact_optimization_plan.md#本轮实现状态更新至-2026-09-08) 为参考；该文档后文保留的早期设计，不应直接视为最新待办。

## 3. OPT-01：Provider 响应正确性

### 3.1 当前问题与依据

[chat-completions-stream.ts](../packages/providers/src/chat-completions-stream.ts) 在读取结束后生成 `response_completed`，未将正常结束与异常 EOF 完整区分。错误 envelope 和无法解析的事件也可能被忽略。

[model-step.ts](../packages/agent/src/model-step.ts) 主要检查是否收到事件，没有独立要求请求具有有效完成事实。因此解析器生成的完成事件会使空流或截断流通过检查。

[openai-compatible-provider.ts](../packages/providers/src/openai-compatible-provider.ts) 默认使用覆盖整个请求的 90 秒超时；429 / 5xx 已有分类，但尚未建立通用的有界重试策略。

### 3.2 设计

1. 在协议适配层记录有效内容、完成信号、服务端错误和解析异常。根据适配器声明判定结束条件，保留合法的供应商协议差异；不能仅将连接 EOF 当作成功，也不能只机械要求某一种结束标记。
2. 在模型步骤层再次检查完成事实。空响应、截断、协议错误和服务端错误产生可区分的失败结果；部分文字可以保留，但不能成为成功的最终回答。
3. 分开处理连接 / 响应头超时、首个有效输出超时、流空闲超时和请求总期限。持续有输出不能无限延长总预算，长响应也不应仅因超过固定短期限被无差别中断。
4. 对适合重试的连接错误、429 和部分 5xx 做有限重试，支持服务端等待提示、退避和取消。重试次数与等待时间计入总期限。
5. 第一版自动重试限制在尚未向用户发布增量、尚未提交该次模型响应的阶段。后续如支持部分输出后的重试，必须建立 attempt 身份及明确的替换规则，避免重复拼接。
6. 已执行工具后，从持久化 operation 状态继续；不通过重跑整轮来恢复模型连接。

### 3.3 验收

- 空流、半段文本后 EOF、半段 tool arguments、错误 envelope、损坏事件均不会静默成功。
- 合法分块、不同换行形式、合法完成信号及 usage 尾事件保持兼容。
- 请求取消会停止网络读取与重试等待。
- 429 / 5xx 重试有上限，已产生的工具副作用不会被重复执行。
- 使用可控流和假时钟覆盖边界；不依赖真实模型接口完成回归测试。

## 4. OPT-02 / OPT-03：持久化恢复闭环

### 4.1 当前问题与依据

[recovery-coordinator.ts](../packages/app-service/src/recovery-coordinator.ts) 会将无法证明已完成的业务 Run 标为 `interrupted`，但该状态投影没有同步恢复或终止 Runtime operation。

[public/runtime.ts](../packages/agent-runtime/src/public/runtime.ts) 会拒绝仍被旧 `currentOperationId` 占用的 Lane；[jojo-app-service.ts](../packages/app-service/src/jojo-app-service.ts) 对已标为 `interrupted` 且无 live handle 的 Run 取消操作直接返回。需要通过真实 SQLite 强杀实验确认并覆盖这条恢复缺口。

同一 Runtime 文件中的 `resumeOperation` 只重建部分请求字段，没有完整恢复 instructions、上下文 / 输出预算、actor、workflow、team 等信息。[Desktop Worker](../apps/desktop/src/worker/worker.ts) 的正常运行与恢复路径因而存在配置传递差异。

### 4.2 恢复职责

| 层 | 职责 |
|---|---|
| Runtime | 判断 operation 状态、恢复或终止执行、维护 Lane 占用不变量 |
| App Service | 将 Runtime 的持久事实投影到业务 Run 与审批状态 |
| Desktop / Server Host | 重建环境、获取当前配置与凭据、呈现恢复入口和结果 |
| Storage | 原子提交 operation 状态与 Lane 变更，保证重复对账安全 |

复用 [sqlite-runtime-store.ts](../packages/storage/src/sqlite-runtime-store.ts) 已有的终态写入与条件解锁事务。不要由 Host 直接清空 `currentOperationId`，也不要先解锁、再补写 operation 终态。解锁必须绑定预期旧 operation，不能释放新任务持有的 Lane。

### 4.3 恢复决策

| 持久状态 | 行为 |
|---|---|
| 已有完整终态 | 投影既有结果，保持幂等 |
| 可恢复检查点，环境可重建 | 通过 Runtime 恢复入口继续 |
| 需要审批 | 重新验证当前授权，按规则生成新的待审批状态 |
| 外部效果可能发生、结果尚未落盘 | 保留不确定效果状态，提供核查信息；不自动重放危险操作 |
| 无法恢复或明确放弃 | 通过 Runtime 原子终止 operation 并释放对应 Lane |
| 数据损坏或状态矛盾 | 报告诊断信息，不猜测性恢复，不强行清锁 |

现有 `interrupted_uncertain_effect` 语义应保留。写文件、发消息等操作不能因为缺少结果记录就认定尚未发生。

### 4.4 执行配置快照

为 operation 持久化版本化执行配置，至少覆盖 provider / model、instructions、上下文与输出预算、资源预算、actor、原始 trigger、workflow / team 归属和执行范围。恢复动作另记审计事件，不覆盖原始任务来源。

快照保存执行语义，不保存凭据明文，也不把旧审批或旧授权当作当前许可。恢复时重新解析 Provider、工具、密钥引用和当前权限。原模型、工作区或必要配置不可用时，返回可解释的恢复失败，不静默更换模型或退回默认身份。

历史 operation 缺少快照时采用显式兼容策略：能从可信持久数据确定的字段才补全；无法确定且影响身份、权限或执行范围的字段不得猜测。

历史 Run 结果绑定其完成时的 entry / leaf 或不可变结果快照，不能从 Lane 后续最新历史推导旧任务的最终结果。

### 4.5 验收

- 在模型请求中、审批等待中、工具执行后结果落盘前、终态事务提交前后分别强杀进程并重启。
- 重复启动和重复对账不会产生重复工具效果、重复终态或错误释放 Lane。
- 旧任务恢复或终止后，同一会话可以开始新任务。
- 自定义 instructions、小上下文 / 输出预算、非 main actor 在恢复前后保持正确语义。
- 恢复后权限收紧或凭据缺失能够被识别，旧审批不能绕过新策略。
- 同一 Lane 完成后续任务，不改变旧 Run 的查询结果。

## 5. OPT-04：Artifact 内容一致性

### 5.1 当前问题与依据

[artifact-storage.ts](../packages/tools-node/src/artifact-storage.ts) 根据历史记录识别产物身份，然后读取工作区当前字节。[ArtifactPanel.tsx](../apps/desktop/src/renderer/artifacts/ArtifactPanel.tsx) 使用历史 version / revision 作为预览缓存键，保存操作再次读取当前文件。

因此外部修改后可能出现旧预览、新下载与未变化的版本标签。现有 revision 记录不能被解释成已经保存历史二进制快照。

### 5.2 第一阶段语义

| 类型 | 读取语义 | 界面表达 |
|---|---|---|
| Conversation Artifact | 读取消息中保存的内容 | 对话中保存的文档 |
| Workspace Artifact | 读取当前被授权文件，并返回实际内容 revision | 当前文件；显示内容是否变化 |
| 历史内容快照 | 后续独立能力 | 只有保存了对应字节后才承诺可查看历史版本 |

历史 version 可保留为已记录更新次数；界面避免让它看起来是当前预览字节的不可变版本保证。

### 5.3 实现建议

1. 内容读取返回实际 revision、长度、MIME 和必要的可用状态；revision 根据本次读到的字节计算。
2. 预览缓存使用实际 revision，并提供刷新、已变化、已删除和不可读取的状态。先实现显式刷新，再评估文件监听；监听不能代替读取时的校验。
3. 下载携带预览对应的 expected revision。Host 对同一次稳定读取的字节完成校验与保存；不一致时提示刷新，不静默下载另一份内容。
4. Conversation 内容与 Workspace 内容通过统一内容服务访问，保留各自存储语义。预览消毒结果与原始下载内容分开缓存和标识。
5. Desktop IPC 和 HTTP 同步定义内容一致性契约。HTTP 可采用条件请求；严格 Schema 的新增字段和客户端兼容需一并处理。
6. 旧会话没有 revision 时，在实际读取后建立当前内容标识，不伪造历史快照。

### 5.4 验收

- 打开预览后从外部编辑、删除、替换文件，界面能够发现或通过刷新确认变化。
- 下载得到的原始内容 revision 与此次预览读取一致；不一致时有明确恢复操作。
- 会话切换和过期异步响应不会将旧文件内容写入新面板。
- 越界路径、符号链接逃逸、跨会话 ID、读取中变化等现有拒绝行为保持有效。
- 保存原始 HTML 与隔离预览之间的差异仍有明确说明。

## 6. OPT-05：Desktop 故障处理

[main.ts](../apps/desktop/src/main/main.ts) 当前在 Worker 退出后固定一秒重启；Renderer 崩溃主要写日志。将该机制升级为有状态的恢复流程。

- 建立 `starting / ready / recovering / failed / stopping` 状态，启动成功以 ready 握手为准。
- 增加有限重试、递增退避和连续失败熔断；用户可查看原因并主动重试。
- 恢复期间新请求明确拒绝或进入有容量、期限限制的队列，禁止无限等待。
- 统一待处理请求的超时、退出清理和取消传播，确保 Promise 只结算一次。
- Renderer 恢复重新加载持久状态；未发送草稿如需恢复，应单独定义保存范围和生命周期。
- 诊断记录包含 Host 状态、退出原因、尝试次数与相关 Run 标识；控制日志体积并复用现有脱敏策略。

验收使用真实 Electron 故障注入，覆盖连续 Worker 崩溃、恢复期间提交请求、Renderer 崩溃、用户退出期间的重启抑制和恢复后再次运行。

## 7. OPT-06：长会话性能

### 7.1 存储读取

[public/runtime.ts](../packages/agent-runtime/src/public/runtime.ts) 的 transcript 分页先读取并复制全部消息，再 `slice`。[sqlite-runtime-store.ts](../packages/storage/src/sqlite-runtime-store.ts) 沿祖先链逐条查询和解析；执行循环也会反复读取历史路径。

建议把分页下推到 Storage，并复用 prepared statements，评估批量祖先查询和从 compaction checkpoint 构建上下文。

必须保持分支语义：不同 Lane 可能共享祖先后分叉，不能简单按 `session_id + seq` 读取所有消息。游标应绑定 session、lane、快照 leaf 和稳定位置；第一版建议固定快照翻页，新消息由事件或刷新另行获取。

Checkpoint 不仅是摘要文本，还需保留上下文构建所依赖的工具配对、固定约束和 memory binding 等语义。优化后的投影必须与原实现等价。

### 7.2 Renderer 更新

[main.tsx](../apps/desktop/src/renderer/main.tsx) 的流式事件更新会触发全量 conversation snapshot 重建；[ConversationViews.tsx](../apps/desktop/src/renderer/ConversationViews.tsx) 再遍历轮次与 Artifact。

实施顺序：

1. 对 text delta 和高频 progress 做短窗口合并，审批、取消和终态立即处理；终态前先 flush 已接收的增量。
2. 拆开稳定历史投影与当前轮次增量，避免每个 chunk 重建历史节点及轨迹记录。
3. 为已完成轮次保持稳定引用，缓存 Artifact 到轮次的映射，避免重复扫描。
4. 将聊天、侧栏、设置、审批、Artifact 面板状态按领域订阅，缩小更新范围。
5. 在基准确认必要后引入虚拟列表，验证动态高度、代码块、图片、跳转定位与滚动锚点。

### 7.3 基准与验收

| 样本 | 场景 | 指标 |
|---|---|---|
| 100 / 1,000 / 10,000 条合成消息 | 打开会话、首屏与翻页 | p50 / p95 耗时、SQL 次数、峰值内存 |
| 固定速率文本与工具进度流 | 输入、滚动、审批弹出 | React commit 次数、主线程长任务、输入延迟 |
| 分叉 Lane 与压缩历史 | 分页与上下文构建 | 分支隔离、投影等价、构建耗时 |
| 含图片和产物的历史 | 切换会话与关闭面板 | 内存增长、缓存释放、过期响应处理 |

先记录固定机器、运行时版本、构建方式、数据分布和重复次数，再确定绝对性能目标。性能门禁与功能测试分开，避免在普通单元测试中加入易波动的严格耗时断言。每次优化必须证明目标路径成本下降且语义保持一致。

## 8. OPT-07：Artifact 索引与预览成本

[Server Artifact 路由](../packages/server-http/src/server.ts) 当前分页读取完整会话历史再识别产物；Desktop 内容通过 Base64 IPC 传递，面板会创建字节数组和字符串；[ArtifactRenderer.tsx](../apps/desktop/src/renderer/artifacts/ArtifactRenderer.tsx) 同步执行解析与消毒。

### 8.1 索引

- 索引作为持久消息的派生视图，保存 session / lane / 来源事件、Artifact 身份、最后产生位置、登记 revision 与可用状态。
- 仅消费持久化成功的工具结果，按来源事件幂等更新；支持水位、重建和一致性检查。
- 同一 workspace 路径在不同会话中不能因索引去重而共享授权。
- 初期可用增量内存索引验证收益；持久索引作为可重建缓存迁移，不立即替代历史记录。

### 8.2 内容与缓存

- 按实际 revision、renderer 类型和消毒策略版本缓存预览；限制缓存容量并释放无用对象。
- 按格式设预览成本预算，大文本可以截断或分段显示，下载保留原始内容。
- 先消除无用的 Base64 / 字节 / 字符串复制，再用基准决定是否引入受控资源协议、二进制传输、后台解析或 Range。
- 如增加独立内容 URL，每次请求仍校验会话授权、实际路径和内容边界，禁止暴露通用本地文件访问入口。
- 继续保留当前 20 MiB 交付上限，是否扩大由格式、内存和传输验证决定；不能只修改常量。

验收覆盖 0 / 100 / 1,000 个 Artifact、1 MiB 与接近当前上限的内容、重复打开和关闭、索引重建、权限失败及文件变化。索引结果应与完整历史重放一致，缓存命中不能绕过内容版本或权限校验。

## 9. OPT-08：预算、计量与质量评估

### 9.1 统一预算

[内部资源 guard](../packages/agent/src/loop/guards.ts) 已支持 wall time、总 Token、费用和工具调用数，但 [公共 RunBudget](../packages/agent-runtime/src/public/run.ts) 与 [Server Protocol](../packages/server-protocol/src/index.ts) 尚未完整开放这些字段。

将预算贯通公共 Contract、Runtime、Desktop、Server、Scheduler 和编排入口，并写入可恢复执行配置。新增字段必须同步 Schema、SDK 与兼容测试；严格解析的协议不能假设新增字段天然兼容。

明确预算语义：

- 区分整次任务、单次模型请求与子任务的预算；子任务不能无意扩大父任务剩余预算。
- 区分硬期限与循环检查时的软上限；正在等待的模型或工具需要取消信号，不能只在下一轮检查。
- 允许为最终解释预留有限预算，不能让收尾阶段无界超支。
- Provider 未返回费用或 usage 时记录为未知，不能当作零成本；费用上限只能在计量来源明确时承诺有效。
- 并行子任务如共享总预算，需要预留与结算机制，避免各分支分别消耗同一份余额。

### 9.2 指标与评估集

基于现有 TelemetrySink 与持久 Run 标识采集首个有效输出耗时、模型耗时、工具耗时、重试次数、压缩次数、Token、缓存命中、费用可用性、失败原因和终态。审批等待与实际执行耗时分开统计，父子任务聚合避免重复计费。

建立固定任务评估集，覆盖代码阅读、局部修改、文件产出、附件处理、可控浏览器操作和恢复任务。成功标准使用可检查的最终结果；单独保留可选真实模型评估，不让需要 API Key、费用和外网的测试进入默认离线 CI。

验收关注同一预算下的任务成功率、完成时间、工具调用次数与成本，而不仅是回答长度或输出速度。

## 10. OPT-09：模块边界与发布验证

### 10.1 渐进拆分

基线中 Renderer 主入口约 2,495 行、Worker 约 1,858 行、Main 约 1,657 行。文件长度用于定位职责集中位置，不作为独立重构理由。

| 模块 | 优先抽取内容 | 主入口保留 |
|---|---|---|
| Main | session / artifact / browser / settings IPC、请求注册与清理、Worker 生命周期 | 进程装配与窗口启动 |
| Worker | 主会话执行环境、恢复协调、Scheduler / Team / Workflow 适配 | 公共 Runtime 装配与命令路由 |
| Renderer | 会话状态与投影、设置状态、审批状态、Artifact 选择和布局 | 顶层页面组合 |
| App Service | 恢复对账、Run 终态投影与错误映射 | 面向 Host 的业务接口 |

每次只迁移一个职责并保持公共边界。Host 不新增对 Runtime kernel 内部实现的直接依赖，继续使用已有 lint 边界约束。

### 10.2 发布矩阵

[CI](../.github/workflows/ci.yml) 当前运行于 Ubuntu，并执行 Desktop `package`；[Forge](../apps/desktop/forge.config.ts) 已声明多平台 maker。按实际发布平台逐步增加 macOS 和 Windows 验证。

| 层次 | 检查 |
|---|---|
| 每次提交 | lint、typecheck、离线测试、受影响的边界与协议回归 |
| 集成验证 | Electron 审批、取消、恢复、Artifact 和安装目录启动 |
| 发布候选 | 对应平台 `make`、安装后启动、密钥存储、附件导入、沙箱可用性 |
| 数据兼容 | 上一版本会话读取、迁移中断后重试、备份恢复 |
| 失败诊断 | 上传已有 Playwright trace、测试日志和必要构建信息，遵守脱敏与保留期限 |

签名、公证、自动更新在正式分发工作项中单独规划。涉及不可逆数据迁移时，不承诺旧二进制可以直接读取新数据库；回退方案依赖经过验证的兼容策略或迁移前备份。

## 11. OPT-10：产品能力扩展

基础正确性完成后，按真实使用频率安排扩展。当前优先保持桌面文件交付体验的连续性。

| 顺序 | 能力 | 第一阶段边界 |
|---|---|---|
| 1 | PDF 预览 | 分页、缩放、懒加载、清晰错误状态与原文件下载 |
| 2 | HTML / Markdown 相对图片资源 | 显式登记依赖资源，每个请求受会话授权与路径校验 |
| 3 | 表格只读预览 | 工作表切换、行列截断说明、原文件下载；不执行宏或外部链接 |
| 4 | Office 转换预览 | 需要独立的转换隔离、资源限制、错误及取消机制 |
| 5 | Headless 能力对齐 | 根据远程使用需求迁移 Team / Workflow 等装配并暴露受控 API |

相对资源支持不能把整个工作区默认为可读资源目录；依赖清单需有可信来源，继续拒绝跨会话引用和符号链接逃逸。

Headless Scheduler 当前只接受 Agent Target，见 [scheduler-runtime.ts](../apps/server/src/scheduler-runtime.ts)。扩展 Team / Workflow 时先迁移主机无关服务，再增加 API 和客户端能力声明，不复制 Desktop Worker 的整套实现。Browser、Memory 远程 API 和独立 Web 前端按实际需求分别立项。

历史二进制快照、交互式 HTML、复杂 Office 编辑、可视化 Workflow 编辑器与云同步保留为后续方向。每项都需独立说明用户场景、存储生命周期、权限边界和验收方式。

## 12. 分阶段实施与合并建议

### 阶段 A：正确性与恢复

交付 OPT-01、OPT-02、OPT-03、OPT-04。Provider 修复与 Artifact 一致性可独立推进；恢复配置设计应先于完整恢复流程合并。

建议分别提交：异常流回归与解析修复、版本化执行配置、恢复终态与 Lane 对账、Artifact 内容 revision 契约、预览与下载交互。

阶段退出条件：异常不会误报成功，重启后能恢复或终止旧任务，同一会话可继续运行，下载与当前预览 revision 一致。

### 阶段 B：性能与运行控制

先采集性能基线，交付 OPT-05 至 OPT-08，并启动 OPT-09 的目标平台 CI。索引依赖持久事件的一致性，预览缓存依赖实际内容 revision，预算恢复依赖执行配置快照。

阶段退出条件：有可重复的长会话基准，目标路径成本下降，预算跨入口一致，故障诊断能够关联到具体 Run。

### 阶段 C：产品与发布

交付目标平台发布验证，按需求推进 OPT-10。每种新预览格式独立提供测试、性能数据和降级路径。

阶段退出条件：目标平台安装产物通过验证；新增产物可以打开、理解、下载，失败时有明确可恢复状态。

### 合并与回退要求

- 单个变更围绕一个可验证行为，不把协议迁移、入口重构与多个新 renderer 混在同一次提交。
- 先补缺口对应的回归或基准，再修改行为；不为纯文档或机械移动新增镜像实现的测试。
- 派生索引能够删除并重建；性能缓存能够关闭而不改变结果。
- 已修复的响应判定和授权校验不提供回退到不安全语义的开关。
- 数据结构变化说明 schema 版本、历史数据策略、失败恢复与备份要求。
- PR 描述记录问题、最终行为、验证证据及未覆盖场景，并更新关联任务状态。

## 13. 任务记录模板

后续每个工作项以以下信息维护，不将“代码已提交”直接等同于“验收完成”。

| 字段 | 内容 |
|---|---|
| 编号 / 名称 | 对应 OPT 编号，可拆为子项 |
| 状态 | 待实施 / 实施中 / 待验收 / 已完成 |
| 当前证据 | 复现、代码路径或性能数据 |
| 依赖 | 必须先完成的 Contract、存储或服务变更 |
| 实现范围 | 受影响入口、模块、协议和数据结构 |
| 验收 | 可重复步骤、结果及必要的失败注入 |
| 兼容与回退 | 历史会话、旧客户端、迁移失败处理 |
| 交付记录 | PR / commit、测试日志和基准结果 |

本文随代码实现更新。新增完成状态必须附验证记录；涉及事实变化时同步修订现状和剩余任务，避免长期保留互相冲突的规划描述。
